### A-03 additional network-route prerequisite

The accepted `NetworkProfile` is account-scoped and the Worker currently lacks a production proxy-secret provider. A **pending** browser profile has no `account_id`, so DX-09 must decide the network route **before** launching a browser for login. A clearly labeled `DIRECT`-only MVP is valid only if the operator did not require a configured account proxy; if a proxy is required, block onboarding until a reviewed pre-account route/secret design exists. Never silently sign in directly and switch network route after the session is created. Test unknown/protected proxy credentials fail closed and existing provisioned Account/NetworkProfile workflows remain unaffected.

## 3. Explicit product decisions already settled

- A single **customer-visible** Windows Desktop app and setup; internal process sidecars remain allowed.
- Tauri 2 + Rust supervisor + React/TypeScript UI; Python business/runtime remains intact.
- One provisioned mode per PC: Controller, Worker, Console. Controller/Worker role effectively fixed until explicit decommission/reset; Console reconnects freely.
- One Controller/Workspace, multiple Operator accounts/Workers; dedicated interactive Windows runtime user per Controller/Worker machine.
- X hides UI to tray, explicit Quit stops safely; runtime autostarts only after Windows user login, never before login/logout. A Windows Service is *deferred*, not secretly installed.
- Static/DHCP-reserved stable LAN endpoint, application-private HTTPS trust and human first-contact verification; no autodiscovery for v1.
- Human Operator login on all modes, including local Controller and Worker. Worker account onboarding is human-assisted **on the Worker**, while Controller remains Account authority. Worker re-pair is explicit decommission and old profile quarantine.
- Deferred: native backup/restore/owner recovery key, Gmail/email recovery channel, automatic updates, Internet/relay, MFA/SSO, HA, cross-Worker browser profile migration.
